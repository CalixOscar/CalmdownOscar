How I work

Write the spec. Build. Check.

I run a one-person studio. AI helps me plan, build and check the work; I own the decisions.

From idea to result

  1. 01 · Question the idea

    I start with the Idea clinic to check what already exists, challenge my assumptions and choose a small test before building.

    I can fill in the questionnaire myself and take its critique prompt to the AI I already use, or ask an LLM to handle the whole process and read the findings back to me. An assistant that supports WebMCP can get the prompt directly from the page.

  2. 02 · Write the spec

    I work from a written spec. I name who the work is for, the task, scope, constraints and what a passing result looks like. Significant changes get an intent, a plan and review; small edits stay small.

  3. 03 · Build in Orca

    In Orca, I give a builder a bounded brief and an isolated task branch or worktree. The brief says what can change and how to check it.

    I create my own agents and workflows around the tasks I repeat.

  4. 04 · Check the result

    I review the diff and run relevant tests. For web work, I also check real browser paths with Jev Browser Control: Jev clicks, types and scrolls while the main assistant defines the goal and checks the outcome.

  5. 05 · Keep the context

    Unli Rice retrieves decisions, guardrails and next steps through MCP. I check the repository for current technical facts.

My current choices

I use stronger reasoning for uncertain decisions and smaller models for well-specified work. That keeps usage for the decisions that need it.

  • Claude

    Opus for planning and review; Sonnet or Haiku for scoped builds when I work in Claude.

  • Sol

    Routine planning and review.

  • Astra

    Complex architecture and unresolved tradeoffs.

  • Terra

    Implementation from a bounded spec.

  • Luna

    Small mechanical edits.

I use a review bridge between Claude and Codex: the model that did not plan the work reviews it. A pre-mortem challenges the plan before the build; a post-mortem checks the finished changes against it. Findings and replies stay in a shared review document.

## Codex — pre-mortem — 2026-11-07

Verdict: revise before building. Fixed, escaped snippets are a sound fit for the phone/offline learning intent, and the current verifier reports no answer mismatches on Python 3.9.6. However, copying Bianca's worker would delete other apps' offline caches, its refresh logic does not guarantee the promised next-visit update, and the try-out still carries persistent streak rewards contrary to the studio rule. The plan also needs explicit acceptance cases for offline entry URLs, installation readiness, assisted answers, accessibility and verifier limitations. These are review recommendations, not implemented corrections; no production code or plan was changed.

**Findings — most consequential first**

1. **high — Activation deletes other apps' offline caches.**
   Scenario: installing/updating PyQuiz with the copied activation handler erases Bianca's and Lastminute's caches; later, activating Bianca's existing worker erases PyQuiz's cache even if PyQuiz's own cleanup is fixed. A user who prepared both quizzes online can then lose offline access to one.
   Verified evidence: `biancaexam/sw.js:9–10` deletes every cache name other than `VERSION`, without an app prefix. A Node VM invocation of the actual activation handler with keys `biancaexam-v1`, `biancaexam-v2`, `pyquiz-v1`, `lastminute-v1` deleted `biancaexam-v1`, `pyquiz-v1`, `lastminute-v1`. Worker scope does not constrain the names that this handler deletes. The proposed copy is in `docs/PLAN-pyquiz.md:52–55`. A safe local precedent already exists at `lastminute/sw.js:3`, which filters by its own prefix.
   Correction: require deletion of only obsolete caches belonging to that app. Revise the plan to address the existing Bianca cleanup too; changing only the new worker leaves the reverse failure intact. Verify coexistence by activating each worker with both apps' caches present, then reopening each offline.

2. **high — Corrected cards can remain stale beyond the next visit.**
   Scenario: a cached incorrect explanation is corrected online, but the learner keeps seeing the old page. Conversely, an immediately activated worker takes over an old open page without a clear update boundary.
   Verified evidence: `biancaexam/sw.js:20–23` returns a cache hit while starting a network refresh; the refresh and `cache.put` are not attached to `e.waitUntil`, and `cache.put` is not awaited. `skipWaiting()` and `clients.claim()` are unconditional (`:7–10`). Registration at `biancaexam/index.html:597` has a synchronous try/catch but no rejection handler, update notice or readiness state. `docs/PLAN-pyquiz.md:78–79` promises a new page on the visit after a reload, which this code cannot guarantee. A bumped version can precache a new shell, but does not reload an already running document.
   Correction: define when an open round adopts an update; retain the background fetch/cache write with `waitUntil`, await writes, handle registration failures, and provide a clear reload/update path at a safe round boundary. Keep version bumps for content changes. Verify an actual v1 → v2 card correction with an open round, online reload, closed/reopened app and subsequent offline launch; do not equate an offline reload test with an update test. Browser lifecycle behavior remains unverified here.

3. **high — The offline promise excludes cold starts and noncanonical entry URLs.**
   Scenario: the founder visits briefly on a weak connection, leaves before precaching finishes, then opens the quiz in airplane mode. Even after successful preparation, entering `/pyQuiz`, `/pyquiz` or `/pyquiz/` offline can require an unreachable server redirect.
   Verified evidence: the intended registration scope is `/pyQuiz/`, with a capital Q and trailing slash (`docs/PLAN-pyquiz.md:50–55`); the other spellings are server redirects, not entries in that scope. Bianca waits for `cache.addAll(FILES)` before installing (`biancaexam/sw.js:4–7`), but its page does not expose cache readiness (`biancaexam/index.html:597`). The current `vercel.json:3–104` has no PyQuiz redirects yet, as expected before implementation. `docs/intent/INTENT-004-pyquiz.md:19–26` makes unreliable connectivity central to success.
   Correction: promise offline use only after a successful online preparation, report readiness/failure, and make all links and the manifest launch URL exactly `/pyQuiz/`. Keep the worker narrowly scoped; do not broaden it to `/` to intercept aliases. Separately test a fresh offline visit (expected unavailable), interrupted/failed install, a prepared canonical offline launch and each alias online/offline. Do not promise offline aliases based on HTTP redirect caching. Verify Vercel's actual redirect chain and final URL when network checks are authorized; that behavior is unverified in this review.

4. **high — The inherited streak system conflicts with the explicit product rule.**
   Scenario: a learner protects or chases a personal record instead of calmly reviewing missed material. Calling it an in-round run does not remove the pressure when the record persists across sessions and consecutive answers increase rewards.
   Verified evidence: the applicable parent-repository `AGENTS.md:22–23` explicitly lists streaks under “no engagement bait”; `docs/intent/INTENT-004-pyquiz.md:30–32` rejects streak chasing. Despite `docs/PLAN-pyquiz.md:42–44` describing an in-round counter, `docs/pyquiz/template.html:103–104,130,172–174,203` saves and displays `mem.best`, pays `10 + min(streak, 10)` XP and shows the best record after a round. Bianca has the same persistence and bonus (`biancaexam/index.html:528–530,556`). The finish copy also urges another round (`docs/pyquiz/template.html:199`).
   Correction: remove persistent best-streak records, consecutive-answer bonuses and streak-chasing copy from the copied behavior. Retain useful finite-round progress and first-attempt results. XP is not automatically prohibited as a neutral measure, but the current streak-linked reward is; merely renaming its label does not satisfy the rule. Any exception belongs with the founder/planner, not an implementation assumption.

5. **medium — 50:50 needs an explicit mastery and scoring contract.**
   Scenario: a learner enables help, gets every two-choice question right, and reads a full first-attempt score as evidence of unaided knowledge. A previously known card remains known after an assisted correct answer, even though the plan can be read as saying helped cards must not be known. A keyboard shortcut may also select an invisible choice if only the CSS is copied.
   Verified evidence: `docs/PLAN-pyquiz.md:39–41` specifies two hidden wrong answers, less XP and no new known mark. Bianca implements a saved switch (`biancaexam/index.html:462,577`), hides/disables two wrong choices and guards hidden indices in `pick` (`:509–519`). It still increments the consecutive-answer counter and counts assisted first answers in the score (`:525–530,551–556`); skipping the mastery assignment preserves a previous `o`. The PyQuiz try-out currently has neither help state nor the hidden-index guard (`docs/pyquiz/template.html:152,163–174,230–233`).
   Correction: explicitly define assisted success as no promotion to known, preserve existing mastery on that success, and mark an assisted miss weak; explain that distinction in the interface. Label assisted results so a mock-test score cannot imply unaided performance. Preserve exactly the correct option and one wrong option, remove hidden options from focus/accessibility, and reject their mouse/programmatic/numeric-key selections. Verify help off/on, new/weak/known cards, misses and retries; help must stay in force for a round begun with it enabled, and inability to save the toggle must not break the round. These are proposed acceptance semantics, not observed PyQuiz behavior.

6. **medium — The answer verifier is narrower than the “every answer” claim.**
   Scenario: a future card prints before failing, contains a main guard, or relies on Python-version/set-order behavior. The authoring check passes while the displayed answer omits observable output or differs from running `main.py` normally.
   Verified evidence: `python3 -I docs/pyquiz/cards.py /dev/null` exited 0 with `52 cards, 48 verified against real Python, 0 problems`; `python3 --version` was `Python 3.9.6`. Four concept answers and all explanations are unchecked. `cards.py:136` uses `exec(code, {})`: functions do share that globals namespace, but normal script metadata is absent. Loading just the definitions in memory and calling the actual `run` produced `('builtins', None)` for `print(__name__)`, and `('', None)` for an `if __name__ == '__main__': print('hi')` snippet. `run('print("hi")\n1 / 0')` returned `('hi', 'ZeroDivisionError')`, but `cards.py:149` checks only the exception name for error cards. `:137–139` strips all trailing newlines: even `print("hi\n")` is reduced to `'hi'`. Feedback at `docs/pyquiz/template.html:183–184` presents only `c.a`. The current error cards (`cards.py:120–129`) do not print before failing; this is an expansion hazard, not a demonstrated current answer mismatch. The home claim “Every answer here was checked” (`template.html:128`) is already broader than the 48 checks.
   Correction: state the tested Python version and distinguish executed snippets from manually reviewed concepts/explanations. Verify under the declared 3.9 baseline and a current supported interpreter before claiming compatibility, excluding nondeterministic set representations. Give execution an explicit script namespace if script behavior is intended. Check stdout and exception together, or reject error cards with nonempty stdout; define exactly which terminal newline is presentation-only. Validate the card schema/check modes and exactly three distinct wrong choices. `cards.py:145` checks four distinct values, not the length of the wrong-option list; duplicated extra options can slip through. Also implement the planned file-code rejection: no `open(` guard currently exists at `:132–160`. `-I` isolates interpreter startup, not trusted snippet execution or filesystem access; do not describe this authoring runner as a security sandbox.

7. **medium — Several explanations teach rules more broadly than Python supports.**
   Scenario: the learner transfers a memorable rule to negative numbers, floats, nonboolean operands or cleanup code and predicts the wrong behavior despite the displayed card itself having the correct answer.
   Verified evidence and recommended corrections:
   - `numbers2`, `cards.py:44–45`: “throws away the leftover part” and “whole number” blur floor division with truncation and integer result type. Actual `run('print(-7 // 2)\nprint(7.0 // 2)')` returned `('-4\n3.0', None)`. Explain floor division toward negative infinity; a float operand can give a float result.
   - `logic4`, `cards.py:88–89`: `and` does not generally return a boolean. Actual `run('print(2 and 3)')` returned `('3', None)`. Limit the explanation to the shown boolean operands, then state that `and` short-circuits and returns an operand.
   - `errors5`, `cards.py:128–129`: “int() only understands digits” is misleading. Actual `run('print(int(" -4 "))')` returned `('-4', None)`. Say that `"five"` is not a valid integer string; signs and surrounding whitespace are accepted.
   - `funcs4`, `cards.py:116–117`: “Nothing after it in the function runs” overlooks cleanup. A probe using `try: return 1` followed by `finally: print("cleanup")` returned `('cleanup\n1', None)`. Say that `return` exits normal function execution after required cleanup.
   These are verified explanatory counterexamples, not wrong answers in the current deck. Review the new explanations manually as well as running the output verifier.

8. **medium — Storage exceptions are contained, but malformed state and durability are not.**
   Scenario: the quiz works during a storage-denied session but silently forgets progress on reopening; a valid JSON value with an invalid shape can also stop mastery updates. Later card insertions can transfer saved progress to the wrong card.
   Verified evidence: `docs/pyquiz/template.html:103–104` catches read/write errors and retains in-memory state. A Node VM execution of the actual inline script with throwing storage methods survived home → save → home and retained `mem.st.basics1 === 'o'`. However, `load()` accepts any truthy `m.st`; the same probe accepted `{"st":true}` and a subsequent `mem.st.basics1='o'` read back `undefined`. It also accepted `{"st":{},"best":"oops"}`. IDs are derived from per-topic position (`cards.py:141–144`), so inserting a card before an existing one changes its identity while the storage key stays `pylearn-quiz-v1` (`template.html:99`).
   Correction: validate/normalize stored state, use explicit stable card IDs before expanding the deck, and handle failed persistence with a quiet, truthful “progress stays for this session” message. Test denied reads/writes, quota failure, malformed JSON, valid JSON of the wrong shape, reload, reset and deck updates. Browser eviction, Safari-versus-home-screen storage sharing and progress transfer are unverified; do not promise durability or shared progress across those contexts.

9. **medium — Buttons are semantic, but question and feedback navigation need verification.**
   Scenario: a keyboard/VoiceOver learner submits an answer, lands on Next before hearing the explanation, then advances and loses the question position. Long Python punctuation/output may also be unclear when spoken, or the whole app may be repeatedly announced.
   Verified evidence: the template uses real buttons, escaped option text and visible focus (`docs/pyquiz/template.html:40,160`), and includes textual feedback plus the correct answer (`:183–193`); it does not rely solely on red/green. However, the entire replaceable main is `aria-live="polite"` (`:91`), `.q` is a div without an associated option-group label (`:158–160`), focus is moved straight to Next (`:193`), and replacing the full main in `question()`/`finish()` supplies no new focus target (`:150–161,197–209`). Reduced-motion CSS is present (`:87`), but the explicit smooth scroll still runs (`:194`). The numeric shortcut ignores modifier keys and focused control context (`:230–233`).
   Correction: label/group answers with the question, make new-question focus deliberate, announce concise feedback through a dedicated status region, and provide an accessible association with the full explanation. Preserve native Enter/Space behavior and ignore modified/text-entry shortcuts. Honor reduced motion in JavaScript scrolling as well as CSS. Verify actual keyboard and VoiceOver reading order, punctuation/multiline output, 50:50 hidden choices, focus after Next/finish/home, zoom and phone touch targets. These are source-level risks; no assistive-technology or visual browser result is claimed.

10. **medium — iOS home-screen installation is not covered by the planned Chrome check.**
    Scenario: the founder saves a shortcut with the wrong launch path/icon, sees desktop-scale content on a phone, or assumes that installation means the offline shell is ready.
    Verified evidence: the try-out starts with only a title and a nonstandard `claude:viewport-fit-sides` meta (`docs/pyquiz/template.html:1–5`); it has no document language, standard viewport, manifest link or Apple touch link. Bianca supplies the proper document shell and installation metadata (`biancaexam/index.html:1–12`), while its manifest uses explicit app-local `start_url`/`scope` (`biancaexam/manifest.webmanifest:5–7`). The plan names icons but only headless Chrome acceptance (`docs/PLAN-pyquiz.md:56–57,68–70`). Bianca's precache list omits its maskable icon even though the manifest references it (`biancaexam/sw.js:4`; `manifest.webmanifest:13`).
    Correction: carry over the complete HTML shell with PyQuiz metadata and exact `/pyQuiz/` launch/scope URLs, standard mobile viewport and the 180px Apple touch icon; precache every required local installation asset, including the maskable icon. Provide concise installation guidance appropriate to the device. Assumption requiring real-device verification: Safari's Add to Home Screen flow must be tested separately rather than inferred from a Chromium install event. Verify standalone launch, icon/title, safe areas, large text, online preparation followed by a closed-app airplane-mode launch, and storage behavior on the target iPhone. No iOS version-specific install behavior was verified offline here.

11. **low — The root CSP fits the proposed app, provided the template's external fonts are removed.**
    Scenario: a literal template copy requests Google Fonts, produces blocked-resource errors and unexpectedly falls back; a deployment that omits generated files fails because authoring sources are excluded.
    Verified evidence: `vercel.json:239–243` includes `/pyQuiz/` under the root rule, allows same-origin resources plus inline script/style, and restricts fonts to self. With no explicit `worker-src`, the same-origin worker is permitted by the script/default fallback; no CSP relaxation is indicated for this static design. `docs/pyquiz/template.html:3–5,13–15` still requests external fonts, contrary to `docs/PLAN-pyquiz.md:45–49`. `.vercelignore:14` excludes the card source, template and planned build script. The existing insertion point is after Norsksti (`playground/index.html:230–243`); its description/OG description and intro are at `:12–14,227`.
    Correction: remove font links/preconnects and use the planned system stacks. Generate and verify the complete `pyQuiz/` output before uploading; do not expect deployed `docs/` files to generate or supply cards. Keep playground links canonical and the screenshot a real capture with the specified dimensions/alt text/size. CSP fit here is a configuration inspection, not a verified live-header or browser-console result.

## Claude — response and settlement — 2026-11-07

Checked against source before answering. Finding 1 is real: `biancaexam/sw.js:9–10` deletes every cache that is not its own `VERSION`, and Cache Storage is per origin, so it also deletes `lastminute` caches today.

1. **Accepted.** PyQuiz cleans only `pyquiz-*` caches. Bianca's activation is narrowed to `biancaexam-*` (one-line fix, version bumped to `biancaexam-v3`). That is a change to a live app, and the founder will be told.
2. **Accepted, simpler.** Navigations go network-first with a 3 s timeout, then fall back to the cache. Other files are cache-first, with the refresh inside `waitUntil` and writes awaited. Online visits therefore always get the newest cards. The page is one self-contained file, so a new worker claiming an open page cannot break a round. No update banner.
3. **Accepted.** The home screen shows "Ready to use offline" only after the worker is active and the page is in its cache. Otherwise it says "Open once with internet to use offline". The manifest, links and scope are exactly `/pyQuiz/`. Aliases work online only, and nothing promises otherwise.
4. **Accepted.** Removed the run counter, best record, streak bonus and XP. A round shows a progress bar and its first-try score. Finish copy is neutral.
5. **Accepted as written.** An assisted correct answer does not promote a card and keeps its existing state. An assisted miss marks it weak. Help stays fixed for the round it started with. Results say "with 50:50 help" when help was on. Hidden options are removed from focus and the accessibility tree and cannot be picked by click, key or code.
6. **Accepted.** The verifier now checks the schema, exactly 3 distinct wrong options, empty stdout before an error, forbidden `open(`/`import`/`input(`/`__`, and uses a fresh namespace. Home copy changes to "Every code answer was checked by running it in Python". Ids: append-only rule documented at the top of `cards.py`. A 3.13 run is not available on this machine (unverified). Cards avoid version-sensitive output.
7. **Accepted.** `numbers2`, `logic4`, `funcs4` and `errors5` were reworded. The 62 new cards were read by Claude for misleading rules.
8. **Accepted.** Stored state is validated and normalised. If saving fails, one quiet line says progress stays for this visit only.
9. **Accepted.** A dedicated status region replaces `aria-live` on `main`. Options sit in a group labelled by the question. Each new question focuses its heading. Shortcuts ignore modifier keys. Scrolling respects reduced motion.
10. **Accepted.** Full document shell copied from Bianca, with the maskable icon precached. iPhone Add to Home Screen is for the founder to test on a real device (unverified by tools).
11. **Accepted.** System fonts only. Generated `pyQuiz/` is committed. `docs/` stays unserved.
